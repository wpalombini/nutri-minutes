# ADR 0002: Alembic migrations, Kysely in the web app and incremental schema growth

- **Status:** Accepted
- **Date:** 2026-11-07

## Context
ADR 0001 made the Postgres schema and migrations the contract between the Python workers and the TypeScript web app, and left this ADR to decide which side owns them. Scout, the first agent, is about to need tables. The pipeline will eventually need many more, but most of their shapes can't be known until those agents are built. Those later tables will hold model-generated content, and every published claim must be traceable to how it was produced.

## Decision
- **Migration tool:** Alembic, owned by the Python side. There is one migration tool and one migration history.
- **Migration rules:** every revision has an upgrade and a downgrade, or documents why it cannot be reversed. Revisions are reviewed by hand, including any that are autogenerated. Prefer small, backward-compatible steps (expand, then contract) over relying on downgrades in production.
- **Running migrations:** migrations run as a separate deploy step before the new code starts, never on application start, so several processes can't migrate at once.
- **Web app access:** the web app uses [Kysely](https://kysely.dev/), a typed query builder, with types generated from the database by `kysely-codegen`. It may read and write data, but it does not change the schema. Future clients, such as mobile apps, use the web app's API and never connect to Postgres directly.
- **Schema growth:** tables are added only when the agent or feature that needs them is built, with each agent's or feature's tables in their own migration.
- **Traceability:** model-generated outputs are stored as new versions rather than overwritten, each recording the model and prompt that produced it.
- **Documentation:** `docs/database.md` describes the current schema and changes in the same PR as any migration.

## Consequences
- **Single toolchain for schema changes:** deploying workers does not need Node.js.
- **New dependencies:** the workers depend on Alembic and SQLAlchemy, and the web app on Kysely and `kysely-codegen`.
- **Web app schema changes go through Alembic:** tables the web app owns, such as accounts and billing, are also added as Alembic migrations, usually as plain SQL.
- **Generated types must stay current:** the web app's types are regenerated after each migration, and CI checks they match.
- **More migrations:** adding tables as needed means more small migrations, in exchange for not designing tables for agents that don't exist yet.
- **More storage:** keeping every version of model-generated outputs uses more space than overwriting them, in exchange for being able to trace any published claim.

## Alternatives considered
- **Prisma Migrate, owned by the web app:** it works out of the box in TypeScript. But the workers would then depend on a Node.js tool for their own tables, and workers will write most of the data. Prisma's Python client can't fill the gap, because [its repository](https://github.com/RobertCraigie/prisma-client-py) is archived and no longer maintained.
- **Prisma or Drizzle as the web app's client:** both keep their own schema file, which would be a second definition of the schema to keep in step with Alembic. Kysely reads the database and keeps none.
- **A language-neutral tool such as dbmate, Sqitch or Atlas:** plain SQL owned by neither side. But Python would lose migrations generated from its models, and Atlas's full version is commercial.
- **Hand-run SQL files:** this adds no dependency, but we would have to build our own version tracking and downgrades.
- **Designing the full schema now:** fewer migrations later, but the design would be guesswork for agents that aren't built.
