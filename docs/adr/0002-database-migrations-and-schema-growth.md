# ADR 0002: Alembic migrations and incremental schema growth

- **Status:** Accepted
- **Date:** 2026-11-07

## Context
ADR 0001 made the Postgres schema and migrations the contract between the Python workers and the TypeScript web app, and left this ADR to decide which side owns them. Scout, the first agent, is about to need tables. The pipeline will eventually need many more, but most of their shapes can't be known until those agents are built.

## Decision
- **Migration tool:** Alembic, owned by the Python side. There is one migration tool and one migration history.
- **Migration rules:** every revision has an upgrade and a downgrade, or documents why it cannot be reversed. Revisions are reviewed by hand, including any that are autogenerated.
- **Web app access:** the web app may read and write data, but it does not change the schema. Its TypeScript types are generated from or checked against the database. The tool for this is chosen when the web app is scaffolded.
- **Schema growth:** tables are added only when the agent that needs them is built, each in its own migration.
- **Traceability:** model-generated outputs are stored as new versions rather than overwritten, each recording the model and prompt that produced it.
- **Documentation:** `docs/database.md` describes the current schema and changes in the same PR as any migration.

## Consequences
- **Single toolchain for schema changes:** deploying workers does not need Node.js.
- **New dependencies:** the workers depend on Alembic and SQLAlchemy.
- **More migrations:** adding tables as needed means more small migrations, in exchange for not designing tables for agents that don't exist yet.
- **Web app client stays open:** the web app can still use Prisma as a client later, generating its schema from the database with `prisma db pull`, as long as it does not run Prisma Migrate.

## Alternatives considered
- **Prisma Migrate, owned by the web app:** it works out of the box in TypeScript. But the workers would then depend on a Node.js tool for their own tables, and workers will write most of the data. Prisma's Python client can't fill the gap, because [its repository](https://github.com/RobertCraigie/prisma-client-py) is archived and no longer maintained.
- **Hand-run SQL files:** this adds no dependency, but we would have to build our own version tracking and downgrades.
- **Designing the full schema now:** fewer migrations later, but the design would be guesswork for agents that aren't built.
