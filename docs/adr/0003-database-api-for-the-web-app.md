# ADR 0003: A database API on the VM for the web app and future clients

- **Status:** Proposed
- **Date:** 2026-11-08
- **Amends:** the "Web app access" decision in [ADR 0002](0002-database-migrations-and-schema-growth.md). Everything else in ADR 0002 stands.

## Context
The web app will be hosted on Vercel. Postgres runs in Docker Compose on the VM, bound to `127.0.0.1`, with no inbound ports open to the internet.

ADR 0002 has the web app query Postgres with Kysely, which needs a direct database connection. From Vercel's serverless functions that would mean publishing the Postgres port to the internet. Cloudflare Tunnel can't avoid that here, because reaching a private TCP service through a tunnel needs a Cloudflare client (`cloudflared` or the Cloudflare One client) on the connecting side, and serverless functions can't run one. Vercel's outbound IPs also can't be allowlisted on its standard plans.

Mobile apps are expected later, and ADR 0002 already says they will use an API, never Postgres directly.

An earlier prototype put PostgREST behind a Cloudflare Tunnel and called it from Next.js Server Components. It kept the database off the internet, but showed the risks of that approach:
- its read role could select from the base tables as well as the published views
- it built query filters from unencoded URL input
- it relied on a single static header checked by a WAF rule

## Decision
- **Our own API service:** a small HTTP API written in TypeScript with [Hono](https://hono.dev/) on Node.js. It runs as a service in Docker Compose on the VM, next to the workers, and is the only way clients other than the workers reach the database.
- **Kysely moves to the API:** the API, not the Next.js app, uses Kysely with types generated by `kysely-codegen`. The ADR 0002 rules still apply: it reads and writes data but never changes the schema, and its types are regenerated after each migration.
- **No inbound ports:** a `cloudflared` service in Compose opens an outbound [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/) to an API subdomain. The API listens only on the Compose network.
- **Authenticated at the edge and at the API:**
  - The API subdomain is a Cloudflare Access application whose only policy is Service Auth.
  - The web app sends a [service token](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/) (`CF-Access-Client-Id` and `CF-Access-Client-Secret`) on every request.
  - The API also verifies the Access JWT in the `Cf-Access-Jwt-Assertion` header against the account's signing keys, so a misrouted tunnel can't bypass Access.
- **Explicit, versioned endpoints:**
  - Paths are versioned, starting with `/v1/`.
  - Each endpoint validates its input and returns only the fields the client needs.
  - There is no generic query language, so clients can't compose arbitrary filters.
- **Least-privilege database role:** the API connects as its own login role. That role reads published views only, never base tables, as planned in `docs/database.md`. It gets write access only to the tables the web app owns, such as accounts and billing, when they are added.
- **Server-side only in Next.js:**
  - All data is fetched in Server Components, Route Handlers or Server Actions.
  - The module that calls the API starts with `import 'server-only'`, so importing it from a Client Component fails the build.
  - The API URL and service token are plain environment variables, never `NEXT_PUBLIC_`, so they aren't inlined into the browser bundle.
  - Client Components receive plain, already-filtered props.
  - CI fails if the built client bundle contains the API host or the token variable names.
- **Caching:** pages that show published content use Next.js caching with revalidation, so most visits don't reach the API.
- **Later clients:** mobile apps will use the same API. End-user authentication for them gets its own ADR.

## Consequences
- **One more service to run:** the API and `cloudflared` join the Compose stack, with health checks, logs and alerts like the other services.
- **Kysely stays:** the ADR 0002 choice of query builder and generated types carries over unchanged, only in a different process.
- **One contract for every client:** the web app and future mobile apps use the same endpoints, so access rules live in one place.
- **An extra network hop:** requests go Vercel → Cloudflare → VM. Caching keeps this off most page views.
- **Dependency on Cloudflare Access:** if Access or the tunnel is down, the site can only serve cached pages. The service token must be rotated on a schedule, in Cloudflare and Vercel together.
- **New dependencies:** Hono, `@hono/node-server`, a JWT verification library and an input validation library for the API, plus `server-only` in the web app. Each is pinned and reviewed when added.

## Alternatives considered
- **Expose Postgres publicly with TLS and a read-only role:** keeps Kysely in Next.js with no extra service, but the database is reachable from the internet and its port can't be limited to Vercel's addresses.
- **PostgREST limited to published views:** little code to write, but it exposes a general query language over HTTP. Writes would have to be SQL functions, and the web app would build query strings, which is the pattern that caused filter injection in the prototype. It is also harder to version for mobile apps.
- **A Python API with FastAPI and SQLAlchemy:** reuses the workers' models and language. But the TypeScript clients would need types generated from OpenAPI rather than from the database, and ADR 0002 already chose Kysely for the TypeScript side.
- **Host Next.js on the VM instead of Vercel:** Kysely could connect over the Compose network with nothing exposed, but we would lose Vercel's hosting, previews and CDN.
- **Cloudflare Hyperdrive:** pools and tunnels database connections, but only for Cloudflare Workers, not Vercel functions.
